CodeInspector
                     A Clean Code Evaluator for Student Python Projects
                  Software Construction and Development | Semester Project | Abdul Samad
What it is
CodeInspector is a Python tool that reads a student's Python project folder and checks how clean and
complete it is. It checks the code against the rules taught in our Software Construction and Development
course, then gives a simple report with a score and tips to improve.
What it will cover
•  Function rules from the course: small functions, indent level of one or two, ideal 0 to 2 arguments (flag 3
   or more), one entry and one exit, and avoiding recursion (including whether a recursive call is a tail call).
•  Naming: flags very short or meaningless names (like d or x) and checks whether function names start with
  a verb.
•  Duplicate code: finds functions with very similar bodies.
•  Completeness: missing README or tests, empty functions, and unused imports.
•  AI-use estimate: a rough guess based on style signals, such as very uniform comments or generic
  names.
How it works
•  The user gives the tool the path of a project folder.
•  The tool reads each Python file and breaks it into its structure using Python's built-in ast module. The
  code is only read, never run.
•  Each rule is a separate check. Every check looks at the structure and records any problem it finds.
• A settings file holds the limits (for example, maximum function length or maximum arguments), so rules
  can be changed or turned off.
•  The results are combined into one report: a score for each area, an overall score, and a list of problems
   with file and line.
Boundaries (what it will not do)
•   It works on Python projects only.
•   It does not run the student's code, so it cannot say whether the program works or gives correct output.
•   It checks style and structure, not whether the idea or logic of the project is good.
•  The AI-use number is only a rough estimate. No tool can prove who wrote a piece of code.
• Name checks can only flag names that are too short or too generic. It cannot fully judge whether a name
   "reveals intent".
•   It will not check reuse across projects or teams.
•  The "industry-ready" score is only a combination of the other scores, not a real industry judgement.
Plan to keep the scope small
Phase 1: naming checks and completeness checks, plus the report. Phase 2: function rules (size,
indentation, arguments, returns, recursion). Phase 3, if time allows: duplicate code, the AI-use estimate,
and the overall score.

# CodeInspector - Project Requirements

19 October 2026 | Document revision 0.1.1

Software Construction and Development, IMSciences

Instructor: Engr. Muhammad Umer Haroon

## Project and Member

CodeInspector will review Python student projects for clean code and completeness.

Abdul Samad | BSSE, Group A | Semester 5 | Roll number 2

GitHub: abdulsamad-codes

Repository: https://github.com/abdulsamad-codes/CodeInspector

This is an individual project with instructor permission. I will handle requirements, coding, testing, documentation, and Git updates.

## Problem and Purpose

A program may work but still have confusing names, large functions, inconsistent formatting, or missing documentation. CodeInspector will help students notice these issues and give instructors a starting point for review.

Sir Umer suggested researching PEP 8 when reviewing the idea. The project will use selected PEP 8 style guidance alongside the clean code rules from the course slides.

## What the Tool Should Do

1. Accept a local project folder and find Python files, skipping Git data, virtual environments, and generated files. Avoid following links outside that folder.
2. Read and parse files without running or importing them. Explain invalid paths, syntax errors, and unreadable files; continue with other files where possible.
3. Check selected PEP 8 naming rules: snake_case functions/variables, CapWords classes, lowercase modules/packages, and uppercase constants where identifiable. Respect special names and conventional self/cls arguments.
4. Check selected formatting rules: four-space block indentation, line lengths, blank lines, whitespace, and simple import layout. Start with 79-character code lines and 72-character comment/docstring lines, allowing configuration and valid continuation-line exceptions.
5. Apply course rules about short functions, shallow nesting, argument counts, multiple returns, loop control, and direct recursion. Review tail-call patterns where feasible. These are separate from PEP 8.
6. Identify missing README/test files and empty functions. Recognize common README formats and test_*.py or *_test.py files.
7. Produce a readable report with the rule, file, line where relevant, and a suggestion. Separate PEP 8, course, and completeness findings. Clearly report files that could not be checked.
8. Allow supported checks to be disabled and thresholds changed through a settings file. Reject invalid settings clearly.
9. Later, add unused-import and duplicate-function checks, report export, and scores with an explained calculation. Disabled checks must not reduce scores.
10. After the core works, research AI-use detection. Evaluate false positives before including it; any result must be labelled experimental rather than proof of authorship.

The first interface will be a local command-line tool. AST will handle structure; source text and tokens will support formatting checks.

For course checks, initial configurable limits are 20 physical lines per function, nesting depth 2 including the function body, and 2 explicit parameters excluding self/cls. The 20-line limit is my project choice, not a number specified in the slides. Nested functions will be checked separately.

## Quality Requirements

- Keep analysis local and leave the input files unchanged.
- Use separate, focused functions for reading files, checking rules, and reporting.
- Give understandable errors and consistent results for the same input/settings.
- Target Python 3.11 or newer initially and avoid machine-specific paths.
- Test valid examples, violations, boundary cases, exceptions, and the guarantee that target code is never executed.
- Document supported checks and actual usage as development progresses.

## Priorities and Responsibilities

First complete planning, then file reading/parsing, naming and formatting checks, course rules, completeness checks, settings, and reports. Unused imports, duplicate checks, exports, and scoring follow. AI-use detection comes last as research.

I own all tasks. The current task list is in docs/backlog.md. A task is done when its checks pass, its documentation is updated, and a meaningful commit records the work.

## Assumptions and Limits

The tool is intended for small, readable Python student projects. Syntax support depends on the Python interpreter used. A web interface, database, and cross-team plagiarism detection are outside the initial scope.

Static checks cannot prove correct logic, meaningful names, or good design. Test files do not prove coverage. Dynamic Python behavior may cause missed findings or false positives. A score only summarizes the checks performed; incomplete scans must be marked clearly.

PEP 8 does not ban every short name or set limits on function size and argument counts. Those extra checks come from the course/project. Python does not optimize tail recursion. AI-associated style signals cannot reliably establish authorship.

## Repository and Submission

Use the naming and version conventions in README.md. Keep actual work in meaningful commits and tag significant milestones instead of saving duplicate versions. v0.1.0 marks the planning baseline; the application is not implemented yet.

Update this file and docs/requirements.pdf together as requirements change. Review the work before submitting the public repository URL and the exact committed PDF. Keep the backlog and development history current throughout the semester.

This is my semester project for Software Construction and Development at IMSciences, taught by Engr. Muhammad Umer Haroon. It will read a Python project and suggest improvements to its naming, formatting, functions, and missing documentation.

- Course rules about small functions, nesting, arguments, returns, and recursion.
- Missing README/test files and empty functions.

AI-use detection is also a research goal for later. It cannot prove who wrote a piece of code.

The tool will run locally from the command line. It will use Python's `ast` module for code structure and text/token checks for formatting, without executing the project's code. Reports will show issues, file locations, and suggestions. Supported rules and limits will be configurable.

Use descriptive `snake_case` names for functions, variables, and modules, `CapWords` for classes, and `UPPER_SNAKE_CASE` for constants. Folders and ordinary documents use lowercase names; standard files such as README.md keep their usual names.

Significant milestones use annotated `vMAJOR.MINOR.PATCH` tags: major for incompatible changes after the stable release, minor for features, and patch for fixes. `v0.1.0` marks the initial planning work. `v1.0.0` will mark the first complete version. The requirements and backlog will be updated during the semester.

languages and blurred in others

• Pascal, Ada, Visual Basic — make a strict, formal distinction: function

--- PAGE 25 ---
Call Stack

• When a function calls another function, Python needs to remember
 where to come back to once the inner function finishes.
• It stores this information in a structure called the call stack. Each time
 a function is called, a new frame is pushed onto the stack.
• When the function returns, its frame is popped off. If a function calls
  itself many times without returning, the stack keeps growing, and
  eventually Python raises a RecursionError.





                                                                     Engr. Muhammad Umer Haroon                                                    25

--- PAGE 26 ---
Normal Recursion

• In normal recursion, the recursive call is not the last thing the
  function does. After the recursive call returns, there is still work left to
  do, such as multiplying, adding, or combining results.
• Because of this leftover work, the current frame cannot be thrown
 away. It has to stay on the stack until the inner call finishes, so that it
 can complete its own work afterward.

What Is a Tech Stack
• A tech stack is the collection of technologies used to build and run a
  software application. It usually has several layers.
• The front end is what the user sees, such as a web page or a mobile screen,
 and it is often built with technologies like React, Vue, or plain HTML and
  CSS.
• The back end is the logic and processing that happens on the server, and it
  is often built with languages like Python, Java, Node.js, or Go. The database
  is where data is stored, and common choices include PostgreSQL, MySQL,
 MongoDB, or SQLite.
• The infrastructure is where the application runs, such as a cloud provider, a
  physical server, or a container platform like Docker and Kubernetes.
• There are also supporting tools such as version control with Git, build
  tools, testing frameworks, and monitoring systems.

Why Tech Stack Selection Matters
• Choosing a tech stack  is one of the earliest and most important
  decisions in a project. A good choice makes development faster, hiring
  easier, and maintenance cheaper.
• A bad choice can lock a team into a technology that is hard to hire for,
 expensive to run, or difficult to change later. This is sometimes called
  technical debt, meaning the future cost of a decision made today.
• The decision  is hard because  it  is rarely purely technical.  It also
  involves the skills of the team, the budget, the timeline, the expected
  scale, the long term maintenance plan, and even the preferences of
 the people who will maintain the system after the original developers
  leave.

Criteria for Choosing a Tech Stack
When evaluating a technology, a team should ask several questions.

• How mature is the technology, and has it been around long enough to
 be stable.
• How large and active is the community, because a large community
 means more tutorials, more libraries, and faster answers when
 problems arise.
• How easy is it to hire developers who already know this technology.
 How well does it fit the problem, since a technology that is perfect for
 one kind of application may be a poor fit for another.

• How well does it perform under the expected load. How secure is it,
 and how quickly are security issues fixed.
• How expensive is it to run, both in terms of licensing and in terms of
 cloud or server costs.
• How easy is it to integrate with the other parts of the stack.
• And finally, how likely is it to still be supported five years from now,

Types of Releases

• A major release introduces significant new functionality or makes
 changes that may break compatibility with previous versions. Users
 often need to plan for major releases because they may require
  configuration changes, retraining, or code updates.
• A minor  release adds  smaller  features or improvements while
 remaining compatible with the previous version. Users can usually
 upgrade to a minor release with little risk.
• A patch release contains only bug fixes and security fixes, with no
 new features. Patch releases are meant to be safe and quick to apply.

Release Cadences


A release cadence  is the rhythm at which a team ships releases.
Different teams choose different cadences depending on their product,
their users, and their ability to test and deploy safely.


The right cadence depends on the product. Too frequent, and users feel
overwhelmed and cannot keep up. Too infrequent, and users wait too
long for fixes and features. A good team finds a rhythm that matches
how its users actually work.





                                                                     Engr. Muhammad Umer Haroon                                                    21

--- PAGE 22 ---
• Continuous deployment means changes are released automatically
 as soon as they pass tests, sometimes dozens of times per day. This
  is common in web based products where the team controls the
  entire environment.
• A fixed schedule means releases happen on a predictable
 timetable, such as every two weeks or every month. This is
 common in products where users need time to prepare for
 changes.
• A feature based cadence means releases happen when a set of
 features is ready, without a fixed date. This is common in smaller
 teams or in products with long development cycles.
• An on demand cadence means releases happen only when there is
 a compelling reason, such as a critical bug or a major new
 requirement. This is common in enterprise software and in
 products with infrequent updates.                                                                                                                                       22
                                                                               Engr. Muhammad Umer Haroon

--- PAGE 23 ---
Release Notes and Changelogs
• A release note is a document that accompanies a release and explains
 what is inside it. Good release notes are written for the user, not for
 the developer. They describe new features in plain language, list bug
  fixes, mention any breaking changes, and explain what users need to
 do to upgrade.
• A changelog is a running record of all releases, usually kept in the
  repository, that allows anyone to see the history of the product.
• Together, release notes and changelogs make it possible for users,
 support teams, and future developers to understand what happened
 and when.





                                                                     Engr. Muhammad Umer Haroon                                                    23

--- PAGE 24 ---
Rollback and Canary Releases

• Even  with  careful  testing, some  releases  cause  problems  in
 production. A rollback is the act of reverting to a previous version
 when a release causes issues. Good teams plan for rollbacks in
 advance, so that reverting is a quick and well rehearsed operation
  rather than a panicked scramble.
• A canary release is a technique where a new version is deployed to a
  small subset of users first, so that problems are caught before the
  release reaches everyone.
• If the canary group reports issues, the release can be stopped before
  it affects the full user base.

Versioning

• Versioning  is the practice of assigning a unique identifier to each
  release so that it can be referred to precisely. Without versioning, it
 would be impossible to know which copy of the software a user is
  running, which bugs have been fixed, or which features are available.
  Versioning is a communication tool.





                                                                     Engr. Muhammad Umer Haroon                                                    26

--- PAGE 27 ---
Semantic Versioning


The most widely used versioning scheme is semantic versioning, often
abbreviated as SemVer. In semantic versioning, a version number has
three parts, written as MAJOR.MINOR.PATCH. For example, version
3.7.2 means major version 3, minor version 7, and patch version 2.


This scheme has a clear benefit. A user can look at a version number
and immediately understand the risk of upgrading. Going from 3.7.2 to
3.7.5 is a patch update and is very low risk. Going from 3.7.2 to 3.8.0
adds features but should not break anything. Going from 3.7.2 to 4.0.0
signals that something may break and requires careful planning.



                                                                     Engr. Muhammad Umer Haroon                                                    27

--- PAGE 28 ---
Alternative Versioning Schemes

• Not every project uses semantic versioning. Some projects use date
 based versioning, where the version is derived from the release date,
 such as 2024.09 or 20240915. This is common in projects with a
  regular release schedule, such as Ubuntu, which uses a year and
 month format. Some projects use calendar versioning combined with
 semantic hints.
• The important thing is not which scheme you choose, but that you
 choose one, apply it consistently, and document what it means. A
  version number that no one understands is worse than no version
 number at all.




                                                                     Engr. Muhammad Umer Haroon                                                    28

--- PAGE 29 ---
Patch

• A patch is a small, targeted update that
  fixes a specific problem in a released
  version. Patches are most often used for
  security vulnerabilities and critical bugs,
 but they can also be used for smaller
  corrections. Unlike major or minor
  releases, patches are meant to be
 minimal. They change as little as possible
 so that the risk of introducing new
 problems is low.





                                                                     Engr. Muhammad Umer Haroon                                                    29

--- PAGE 30 ---
Why patching ?

• Bugs exist in every system, and some of those bugs can be exploited
 by attackers. When a security vulnerability becomes public, attackers
 often move quickly to exploit  it.  If users do not apply the patch
 promptly, they remain exposed. This is why security patches are often
 released on an urgent schedule, sometimes within hours or days of a
  vulnerability being discovered.





                                                                     Engr. Muhammad Umer Haroon                                                    30

--- PAGE 31 ---
The Tension Between Speed and Safety
related to patching

• Patching involves a genuine tension. Security teams want patches
 applied as quickly as possible, because every hour of delay is an hour
  of exposure. Operations teams want patches tested thoroughly,
 because a bad patch can break production systems and cause outages
  that are worse than the original vulnerability.
• A good organization manages this tension through clear policies,
 automated testing, staged rollouts, and the ability to roll back quickly
  if something goes wrong. The goal is to manage intelligently.





                                                                     Engr. Muhammad Umer Haroon                                                    31

--- PAGE 32 ---
The Cost of Not Patching

•  Systems remain vulnerable to  attacks, and a  single unpatched
  vulnerability can lead to a data breach, financial loss, and reputational
 damage. Bugs accumulate, and users lose trust.
• The codebase drifts away from current best practices, making future
 changes harder. Eventually, the system becomes so outdated that it
 must be  rewritten, which  is  far more  expensive  than  steady
 maintenance would have been.
• This situation is sometimes called technical bankruptcy, and it is a real
  risk for any project that stops investing in its own health.

RAW STRING

• Raw strings aren’t a different kind of string data type; they’re just a convenient
 way to type string literals that contain several backslash characters.
• We often use raw strings to type the strings for regular expressions or
• Windows file paths, which often have several backslash characters in them that
 would be a pain to escape individually with \\.





                                                   Engr.Muhammad Umer Haroon

--- PAGE 38 ---
• In Python, a raw string is a string literal that is prefixed with the letter `r` or `R`.
  This prefix tells Python to treat backslashes (`\`) as literal characters and not as
  escape characters. This can be particularly useful when dealing with strings that
  contain many backslashes, such as regular expressions or file paths.





                                                   Engr.Muhammad Umer Haroon

--- PAGE 39 ---
No Escape Sequences

   • In a raw string, escape sequences (like `\n`, `\t`, or `\\`) are
    treated as normal characters. For example:
   •   - Regular string: `"Hello\nWorld"` will output:
   •   Hello
   •   World
        - Raw string: `r"Hello\nWorld"` will output:
   • Hello\nWorld





                                                   Engr.Muhammad Umer Haroon

--- PAGE 40 ---
• Raw strings are particularly handy for Windows file paths, where
 backslashes are common. For instance:
•   - Regular string: `"C:\\Users\\John\\Documents"`
•   - Raw string: `r"C:\Users\John\Documents"`





                                                   Engr.Muhammad Umer Haroon

--- PAGE 41 ---
• The raw string feature simplifies working with complex strings and
 enhances code readability

Lookahead and Lookbehind Assertions

• These assertions allow you to match patterns based on what follows
 or precedes them without including those characters in the match.
• Lookahead: (?=...)
• Lookbehind: (?<=...)
